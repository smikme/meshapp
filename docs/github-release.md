# Сборка и публикация через GitHub

Выпуск использует GitHub Actions, Releases, Pages и Secrets. Облачный RPC
`cloud.meshapp.privatepractice.app` и загрузка файлов `d.privatepractice.app`
продолжают работать независимо от выпуска. Сервер Gitea не используется.

## Первоначальная настройка

1. Добавить изменения в `main` репозитория `smikme/meshapp`. Workflow с ручным
   запуском должен присутствовать в основной ветке.
2. Публичный ключ `config/update-public-key.pem` хранится в Git и встраивается в
   приложение. Приватный ключ находится в `.release-secrets/update-private-key.pem`;
   каталог исключён из Git. Сохраните отдельную резервную копию. Новый ключ для
   каждого выпуска не нужен: установленные приложения доверяют прежнему.
3. Установить GitHub CLI, авторизоваться с правами администратора репозитория и
   выполнить из корня проекта:

   ```sh
   gh auth login
   bash scripts/ci/configure-github.sh
   ```

   Команда создаёт environment `production`, разрешает публикацию из `main`,
   сохраняет секрет `MESHAPP_UPDATE_ED25519_PRIVATE_KEY` и включает Pages с
   источником GitHub Actions. Она не публикует приложение.

   При ручной настройке: Settings → Environments → production → Secrets;
   Settings → Pages → Build and deployment → Source: GitHub Actions.
   Если для `github-pages` настроены ограничения веток, разрешите `main`.
4. Разрешить GitHub Actions в репозитории и сделать задания `Check` обязательными
   для слияния PR. Права записи релиза и Pages выделены только своим заданиям.

`scripts/ci/generate-update-key.sh` нужен только для создания первой пары в новом
проекте. Он отказывается перезаписывать существующие ключи. Старые ключи и
сертификаты не требуются. Developer ID и notarization в CI не настроены.

## Ежедневная работа

`Check` запускается для pull request, изменений `main` и вручную. Java-тесты
выполняются на Linux x86_64 и ARM64, Windows и macOS; сценарии публикации — на Linux с OpenSSL 3.
JUnit-отчёты сохраняются как Actions artifacts, в том числе при ошибке тестов.

Используются Temurin 25.0.5+8, Gradle Wrapper 9.8.2 с проверкой SHA-256,
appimagetool 1.9.1 с проверкой SHA-256 и Freedesktop runtime/SDK 25.08 для Flatpak.
Flatpak Builder берётся из официального `org.flatpak.Builder` с закреплённым
коммитом для каждой архитектуры в `scripts/ci/setup-linux.sh`: системная версия Ubuntu 22.04 несовместима
с AppStream современных SDK. Само приложение по-прежнему собирается на Ubuntu
22.04 и упаковывается для runtime 25.08.
Обновление инструментов делается отдельным изменением с проверкой всех платформ.

## Собрать выпуск

### Unstable для тестирования

Push в ветку `unstable/X.Y.Z` запускает полную матрицу сборок. Шаг `prepare`
один раз назначает номер из `GITHUB_RUN_NUMBER`, общий для всех ОС и архитектур.
Версия приложения и тег имеют вид `vX.Y.Z-unstable.N`.

После проверки полного комплекта создаётся черновик prerelease. Его автоматически
подхватывает **Publish release** через `workflow_run`: workflow выполняется из
основной ветки, сверяет SHA завершённой сборки, проверяет пакеты и подпись, затем
публикует prerelease и манифест `updates/unstable/meshapp.json`. Latest и stable-feed
сохраняются. Секрет подписи доступен только заданию публикации в `production`,
код из собранной ветки там не выполняется. Если environment требует подтверждения,
публикация будет ждать его по существующим правилам GitHub.

Сначала новые workflow и сценарии публикации должны попасть в `main`, затем эти
изменения нужно перенести в ветку `unstable/*`. Без обновления основной ветки
автоматическая подпись и публикация нового формата не заработают.

Для ручной unstable-сборки укажите `2.4.0-unstable` в **Build release**. Старый
ввод `2.4.0-unstable.1` также принимается, но номер всегда назначается текущим
запуском CI. Для сборок вне веток `unstable/*` выполните **Publish release** вручную
из `main`, передав полный тег созданного черновика.

### Стабильный черновик

Actions → **Build release** → Run workflow, ветка `main`, версия, например `2.4.0`.
CI добавит номер: `v2.4.0+build.126`. Следующий запуск той же версии создаст
`v2.4.0+build.127`. Версия релиза допускает major/minor до 255, patch до 999.

Повтор упавших заданий сохраняет номер сборки. `GITHUB_RUN_ATTEMPT` служит для
диагностики попытки и не меняет идентичность выпуска. Уже опубликованные пакеты
нельзя пересобирать или заменять; для новой сборки нужен новый запуск workflow.

### Версии приложения, обновлений и установщиков

`version.properties`, `release.json` и подписанный манифест содержат полную
`version`, базовую `releaseVersion`, `channel`, `buildNumber`, `packageVersion`
и прежний `versionCode`. Код `major * 1000000 + minor * 1000 + patch` (минус один
для unstable) сохранён для старых клиентов. Новый updater сравнивает базовую
версию, затем stable/unstable, затем номер сборки численно. Stable выше unstable
той же базовой версии. Окно «О программе» показывает именно номер сборки.

Установщики используют отдельную числовую последовательность, превышающую
старые версии пакетов `2.x`: сборка 126 → `3.0.126`, 65535 → `3.0.65535`,
65536 → `3.1.0`. Формула:
`(3 + N // 16777216).((N // 65536) % 256).(N % 65536)`.
Она соблюдает ограничения MSI и использует три компонента, а не игнорируемый
четвёртый. Допустимы номера 1..4244635647; переполнение останавливает сборку.
Это служебная версия пакета: пользовательская версия приложения остаётся `2.4.0`.

Номер release workflow нельзя сбрасывать. Если workflow переносится или создаётся
заново, нумерацию нужно согласовать с опубликованными выпусками. Публикация
с меньшим или равным номером относительно другого опубликованного выпуска
отклоняется, даже между каналами. Если стабильный черновик устарел, пока выходили
unstable-сборки, запустите новую сборку stable перед публикацией.

Первый stable-выпуск с этой логикой должен повысить базовую версию относительно
установленных старых клиентов: например, `2.4.1`, если уже выпущена `2.4.0`.
Старый updater увидит увеличение `versionCode`; после перехода станут доступны
обновления между сборками одной версии. Старые unstable-клиенты могут перейти
через следующий stable-выпуск либо установку нового пакета вручную.

Workflow фиксирует SHA коммита, запускает тесты и собирает:

| Платформа | Пакеты |
| --- | --- |
| Linux x86_64, Ubuntu 22.04 | DEB, AppImage, Flatpak, self-update ZIP |
| Linux aarch64 (ARM64), Ubuntu 22.04 ARM | DEB, AppImage, Flatpak, self-update ZIP |
| Windows x86_64, Windows 2022 | MSI, self-update ZIP |
| macOS aarch64, macOS 15 | DMG, self-update ZIP |
| macOS x86_64, macOS 15 Intel | DMG, self-update ZIP |

Linux ARM64 собирается на `ubuntu-22.04-arm`. JDK, JavaFX и нативная BLE-библиотека
используют архитектуру runner; `setup-linux.sh` выбирает соответствующие
appimagetool и Flatpak Builder. ARM-пакеты получают идентификатор `linux-aarch64`
в именах файлов и манифесте автообновления. Для локальной сборки нужны Linux ARM64,
JDK 25 для ARM64 и appimagetool для aarch64; команды Gradle те же, что для x86_64.
32-битный ARM в матрицу не входит.

После `verifySelfUpdatePackage` файлы получают имена с версией, ОС и архитектурой.
Проверяются версия и публичный ключ внутри каждого ZIP. Только полный комплект
попадает в черновик GitHub Release вместе с `release.json` и `SHA256SUMS`.
Тег создаётся на SHA, из которого собраны пакеты.

Повторный запуск существующего тега допустим только с тем же SHA, пока релиз
остаётся черновиком. Опубликованные файлы не пересобираются. После изменения
исходников запустите новый Build release; он назначит следующий номер.

## Проверить и опубликовать

Скачать пакеты из черновика, проверить установку, первый запуск, BLE/USB и переход
между двумя версиями нового цикла обновлений. Linux-бинарники также проверить на
минимальной поддерживаемой системе. CI не заменяет тесты реального оборудования.
Mac DMG имеют ad-hoc-подпись: Gatekeeper может потребовать разрешение на запуск.

Отредактировать описание черновика. Затем Actions → **Publish release** → Run
workflow, ветка `main`, полный тег черновика, например `2.4.0+build.126`. Русские release notes можно указать отдельным
полем. Не публикуйте черновик кнопкой GitHub вручную: workflow сначала добавляет
подписанный манифест.

Публикация скачивает готовые файлы, сверяет SHA-256, размеры, SHA коммита,
встроенные версии и ключи. Секрет подписи должен соответствовать ключу сборки.
После проверки Ed25519-подписей workflow публикует релиз с `meshapp.json`, затем
разворачивает Pages. Адреса манифестов:
`https://smikme.github.io/meshapp/updates/stable/meshapp.json` и
`https://smikme.github.io/meshapp/updates/unstable/meshapp.json`.
Stable-клиент читает только stable; unstable-клиент — оба и выбирает новую версию.
Отсутствующий до первой публикации канал (HTTP 404) не мешает второму каналу.
Перед развёртыванием Pages предыдущие подписанные манифесты скачиваются из Releases,
поэтому публикация одного канала не удаляет другой.

Если Pages не развернулся после публикации, повторите **Publish release** с теми
же release notes. Новый манифест должен побайтово совпадать с опубликованным.
Продвижение релиза старее существующего стабильного запрещено. Исправления
доставляются новым номером сборки; более старую версию или сборку публиковать нельзя.

## Каталог Lua, диагностика и Flatpak

Экспорты скриптов формата `meshapp-lua-script` хранятся в основном репозитории,
в ветке `main`: `meshappstore/ru/` для русского интерфейса и `meshappstore/en/`
для всех остальных языков. Клиент получает список файлов через публичный GitHub
Contents API и скачивает экспорты по `download_url` с `raw.githubusercontent.com`.
Регистрация, вход в GitHub и токен не нужны. Изменения скриптов доступны после
добавления в `main`, без публикации нового выпуска приложения.

При публикации выпуска те же папки используются для сборки `store/ru/` и
`store/en/` на Pages, включая `catalog.json`, для совместимости с прежними
клиентами. Каталог Pages и документация публикуются вместе с выпуском.

Диагностика сохраняется локально в `~/.meshapp/reports/`. Приложение открывает
форму GitHub Issue, но не отправляет отчёт. Пользователь проверяет архив и
прикрепляет его сам. Issue публичный; большие дампы памяти могут не поместиться
в ограничение вложений GitHub — тогда прикрепите отдельный лог из архива.
Токенов GitHub или Gitea в клиенте нет.

Пакет `.flatpak` публикуется в GitHub Releases. Для запуска нужна установленная
среда `org.freedesktop.Platform//25.08`. Установка и обновление выполняются из
скачанного файла. Собственный OSTree-репозиторий и SSH не используются.
`app.privatepractice.meshapp.yml` служит для локальной офлайн-сборки текущего
checkout; основной CI использует `./gradlew flatpak`.

Первый выпуск нового цикла устанавливается вручную. Старые клиенты не знают
нового адреса и ключа обновлений.

## Локальные сборки

`./gradlew build`, `jar`, `installDist`, `jpackage`, `appImage`, `flatpak` и задачи
self-update без явно заданной release-версии резервируют один локальный номер
на вызов Gradle. Все пакеты одного вызова используют его. Счётчик находится в
`.gradle/meshapp-local-build-number`, защищён файловой блокировкой и переживает
`clean`. Удаление `.gradle` сбрасывает локальный счётчик. Пропуски после неудачной
сборки допустимы. `test`, `check`, `classes`, синхронизация IDE и `--dry-run`
не увеличивают его. Используйте полные имена задач упаковки.

В версии виден суффикс `+local.N`; `versionCode=0` исключает такие сборки из
публичных обновлений. Локальные номера независимы от CI, такие пакеты нельзя
публиковать в каналы обновлений. Для воспроизводимой проверки release-пакетов
задайте полный тег через `-PmeshappVersion=v2.4.0+build.126` — счётчик не меняется.

## Локальные проверки

```sh
python3 -m unittest discover -s scripts/ci/tests -v
./gradlew test
./gradlew jpackage selfUpdateArchive verifySelfUpdatePackage -PmeshappVersion=v2.4.0+build.126
```

Для AppImage и Flatpak добавьте инструменты и задачи в один вызов Gradle после
`jpackage`: задача `jpackage` очищает выходной каталог.
